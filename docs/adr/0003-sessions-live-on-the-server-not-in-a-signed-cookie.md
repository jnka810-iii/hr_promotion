# เซสชันอยู่ในฐานข้อมูลฝั่งเซิร์ฟเวอร์ ไม่ใช่ cookie ที่เซ็นชื่อ

Flask มี `flask.session` ให้อยู่แล้ว มันเก็บข้อมูลเซสชันไว้ใน cookie ของผู้ใช้เอง แล้วเซ็นชื่อ
กำกับด้วย `SECRET_KEY` เขียนน้อยกว่าและเป็นวิธีมาตรฐาน คนที่มาอ่านโค้ดนี้ครั้งแรกจะถามว่า
ทำไมไม่ใช้ — เอกสารนี้ตอบคำถามนั้น

เลือกเก็บเซสชันเป็นแถวในตาราง `sessions` ของ `hr_promotion.db` โดย cookie ถือเพียงเลขสุ่ม
32 ไบต์จาก `secrets.token_urlsafe` ที่ไม่มีความหมายในตัวเอง ฝั่งเซิร์ฟเวอร์เอาไปค้นหาเจ้าของ

เหตุผลหลักคือ `SECRET_KEY` เป็นคำถามที่ตอบไม่ได้ในบริบทนี้ โปรแกรมนี้ถูกแพ็กเป็น `.exe`
แจกไปวางบนเครื่อง Windows ของหน่วยงาน ที่ผู้ใช้เป็น administrator ของเครื่องตัวเอง คีย์จะไป
อยู่ที่ไหน — ฝังในโค้ดก็เท่ากับทุกเครื่องใช้คีย์เดียวกันและใครถอด `.exe` ออกดูก็ได้ไป; วางเป็น
ไฟล์ข้างฐานข้อมูลก็เป็นไฟล์ที่ผู้ใช้เครื่องนั้นอ่านได้อยู่ดี และกลายเป็นไฟล์ที่สี่ที่ต้องสำรอง
ต้องกันไม่ให้หลุดเข้า git และต้องตอบว่าจะหมุนคีย์ยังไง ใครที่ได้คีย์ไปปลอม cookie ของผู้ดูแล
ระบบได้ทันทีโดยไม่ต้องรู้รหัสผ่านใคร การไม่มีความลับให้เก็บเลยทำให้คำถามทั้งแถบนี้หายไป

เหตุผลที่สองคือการเพิกถอน cookie ที่เซ็นชื่อแล้วเพิกถอนไม่ได้ — เซิร์ฟเวอร์ไม่ได้จำว่าเคยออก
ใบไหนไปบ้าง "ออกจากระบบ" จึงทำได้แค่บอกเบราว์เซอร์ให้ลืม ส่วนใครที่ก็อป cookie ไว้ก่อนหน้า
นั้นยังใช้ต่อได้จนหมดอายุ ซึ่งขัดกับสามอย่างที่ระบบนี้ต้องทำจริง: ปิดบัญชีคนที่ลาออกแล้วต้อง
ตัดทันที, เปลี่ยนรหัสผ่านเพราะสงสัยว่ารหัสรั่วต้องไล่เครื่องอื่นออก, และผู้ดูแลต้องตอบได้ว่า
ตอนนี้บัญชีหนึ่งค้างล็อกอินอยู่กี่เครื่อง

## Consequences

**ทุก request ที่ต้องยืนยันตัวตนมี `SELECT` เพิ่มหนึ่งครั้ง** บน SQLite ที่อยู่บนดิสก์เดียวกัน
ด้วยดัชนี primary key ต้นทุนนี้ไม่มีผลกับขนาดงานระดับหน่วยงาน แต่มันคือ connection เพิ่ม
หนึ่งตัวต่อหนึ่ง request ที่ต้องปิดให้ครบทุกเส้นทางเหมือนทุก call site ของ `get_db()`

**การเลื่อนอายุเซสชันคือการเขียน** จึงเลื่อนเฉพาะเมื่ออายุเหลือน้อยกว่าครึ่งกรอบ ไม่ใช่ทุก
request ไม่งั้นการโหลดตารางหนึ่งครั้งจะไปจับ write lock ของ SQLite แข่งกับการอัปโหลดไฟล์

**ตาราง `sessions` ต้องมีคนเก็บกวาด** ทำตอนเปิดโปรแกรมและตอนล็อกอินสำเร็จ ไม่มี thread
เฝ้า เพราะแอปนี้เปิดปิดเป็นรอบตามวันทำงาน แถวที่หมดอายุแต่ยังค้างอยู่ใช้ล็อกอินไม่ได้อยู่แล้ว
การตรวจเทียบเวลาจริงทุกครั้ง ไม่ได้พึ่งว่าแถวถูกลบไปหรือยัง

**เซสชันอยู่ในไฟล์เดียวกับข้อมูล HR** การ restore สำเนาสำรองของเมื่อวานจึงย้อนตาราง
`users` และ `sessions` กลับไปด้วย: บัญชีที่สร้างหลังจากสำเนานั้นจะหายไป และทุกคนต้อง
ล็อกอินใหม่ แลกกับการที่บัญชีถูกสำรองโดยอัตโนมัติพร้อมข้อมูล โดยไม่มีไฟล์ที่สองให้ลืม

**`app.secret_key` ต้องเป็น `None` ตลอดไป** ถ้าวันหนึ่งมีใครตั้งมันขึ้นมา นั่นแปลว่ามีกลไก
ที่สองเข้ามาในระบบแล้ว และเอกสารนี้ต้องถูกรื้อก่อน (มีเทสต์ปักหมุดไว้)
