# ฐานข้อมูลใช้งานจริงอยู่นอก version control และมีสำเนาสำรองรายวันมาแทน

`hr_promotion.db` ถูก track ไว้ใน git ตั้งแต่ commit แรก ผลคือทุก `git checkout`, สลับสาขา
หรือ `git stash` เขียนข้อมูลที่ผู้ใช้กรอกจริงทับด้วยเวอร์ชันที่ commit ไว้ — ซึ่งมีแค่ 2 commit
ทั้งคู่จากเดือนเมษายน 2026 และทั้งคู่บรรจุข้อมูลทดลอง 4 รายการชุดเดียวกัน อาการที่ผู้ใช้เจอคือ
"เห็นแต่ข้อมูลทดลอง และมันกลับมาเรื่อย ๆ"

หลักฐานที่ชี้ชัดคือความไม่สมมาตร: `static/uploads/*.pdf` อยู่ใน `.gitignore` จึงรอดทุกการ
checkout ส่วนแถวใน `attachments` ที่ชี้ไปหามันไม่รอด เมื่อวัดในวันที่ตัดสินใจเรื่องนี้ ดิสก์มี
PDF 54 ไฟล์ (617 MB) อัปโหลดคร่อม 5 ช่วงเวลาจากเมษายนถึงตุลาคม ขณะที่ `attachments`
มี 0 แถว และ commit ที่มี DB อ้างถึงเพียง 2 ไฟล์ ไฟล์ทั้ง 54 จึงเป็นไฟล์แนบกำพร้า

จึงเอาไฟล์ออกจาก index (`git rm --cached`, ไฟล์บนดิสก์คงอยู่) ให้ `*.db` ใน `.gitignore`
มีผล และเพิ่มสำเนาสำรองรายวันที่ `backup/hr_promotion-YYYYMMDD.db` ถ่ายก่อน `init_db()`
ทุกครั้งที่โปรแกรมเริ่มทำงาน

## Consequences

**การเอาออกจาก index ไม่ปิดช่องทั้งหมด** commit เก่าทุกตัว รวมทั้งทุกสาขาทั้งในเครื่องและบน
remote ยังมีไฟล์นี้อยู่ใน tree การ `git checkout` ไปที่ commit หรือสาขาเหล่านั้นจะเขียนข้อมูล
จริงทับอีกครั้ง การจะปิดช่องให้สนิทต้องลบไฟล์ออกจากประวัติ หรือเอาไฟล์ข้อมูลออกไปอยู่นอก
working tree ของ repo ไปเลย — ทั้งสองอย่างยังไม่ได้ทำ สำเนาสำรองรายวันคือชั้นที่รอด
เหตุการณ์นั้นได้ และเป็นเหตุผลที่มันต้องไม่อยู่ใน git เพราะ git คือต้นเหตุ

**git เลิกเป็นที่สำรองข้อมูล** ซึ่งมันไม่เคยเป็นที่สำรองที่ใช้ได้อยู่แล้ว — มันเก็บแค่สภาพเดือน
เมษายนและเอามาทับของใหม่ แต่หมายความว่าถ้าสำเนาสำรองรายวันพัง จะไม่มีอะไรเหลือ

**สำเนาแรกของวันชนะ** เรียก `_backup_db()` ซ้ำในวันเดียวกันไม่เขียนทับ ตั้งใจให้เป็นแบบนี้
เพราะถ้าเขียนทับทุกครั้งที่เปิดโปรแกรม การเปิดโปรแกรมหลังข้อมูลถูกล้างจะทับสำเนาที่ดี
ด้วยสำเนาที่ว่าง ผลข้างเคียงคืองานที่ทำระหว่างวันไม่มีสำเนา จนถึงเช้าวันรุ่งขึ้น
