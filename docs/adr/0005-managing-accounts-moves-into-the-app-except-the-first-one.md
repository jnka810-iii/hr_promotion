# การจัดการบัญชีย้ายเข้ามาในโปรแกรม ยกเว้นบัญชีแรก

จนถึง 13/11/2026 การสร้างและแก้บัญชีทำได้ที่เดียวคือ `manage_users.py` บนเครื่องเซิร์ฟเวอร์
เอกสารสองที่เขียนกฎนี้ไว้ชัดเจน: `README.md` บอกว่า "การจัดการบัญชีไม่ได้ผูกกับบทบาท ใครนั่ง
หน้าเครื่องเซิร์ฟเวอร์ได้ก็รัน `manage_users.py` ได้" และ `GLOSSARY.md` นิยามความต่างของบทบาท
ว่าคือ "การล้างข้อมูลทั้งระบบและการจัดการบัญชี ซึ่งเป็นของผู้ดูแลระบบเท่านั้น"

เอกสารนี้กลับคำนั้น และบอกว่ากลับเฉพาะส่วนไหน

## สิ่งที่เปลี่ยน

มีแท็บ **จัดการผู้ใช้งาน** ในโปรแกรม เห็นบัญชีทั้งหมด เพิ่มบัญชี แก้ชื่อ เปลี่ยนบทบาท
ตั้งรหัสผ่านใหม่ และปิดหรือเปิดบัญชีได้ หลัง**เข้าสู่ระบบแล้ว**เท่านั้น

`manage_users.py` ยังอยู่ครบทุกคำสั่ง ไม่ได้ถูกลดเหลือ wrapper และไม่ได้ถูกประกาศว่าเลิกใช้

## ทำไมกฎเดิมถึงถูกในตอนนั้น

เหตุผลเดิมไม่ได้ผิด มันตอบคำถามที่แคบกว่าที่เราเคยคิด

ตอนเขียน ADR 0004 สิ่งที่เรากลัวคือ**หน้าสร้างบัญชีที่ไม่ต้องล็อกอิน** หน้านั้นจะเป็น endpoint
ที่เขียนข้อมูลได้โดยไม่มีด่าน เปิดอยู่บนพอร์ตที่ทั้งวง LAN เข้าถึง และจะกลับมาเปิดอีกทุกครั้งที่
ตาราง `users` ว่าง รวมถึงตอน restore สำเนาสำรองผิดไฟล์ ใครในวงที่เปิดหน้านั้นทันก่อนเจ้าของ
ระบบก็ได้เป็นผู้ดูแล นั่นคือรูจริง และมันยังเป็นรูอยู่

แต่ "หน้าสร้างบัญชีแรกที่ไม่ต้องล็อกอิน" กับ "แท็บจัดการบัญชีที่อยู่หลังด่าน" เป็นคนละอย่าง
อันหลังเข้าถึงได้เฉพาะคนที่มีบัญชีอยู่แล้วและพิสูจน์ตัวตนผ่านแล้ว ซึ่งเป็นคนกลุ่มเดียวกับที่
เดินไปหน้าเครื่องเซิร์ฟเวอร์ได้อยู่แล้วในทางปฏิบัติ

## ทำไมถึงต้องเปลี่ยน

ข้อเดียว: **`manage_users.py` ต้องมี Python รันได้** ระบบนี้ถูกแพ็กเป็น `.exe` ไปวางบนเครื่อง
ที่ไม่มี Python เครื่องเหล่านั้นจึงแก้บัญชีไม่ได้เลย ไม่ว่าจะเรื่องเล็กแค่ไหน คนลาออกแล้ว
ปิดบัญชีไม่ได้ ลืมรหัสผ่านแล้วตั้งใหม่ให้ไม่ได้ ทางแก้เดิมคือให้คนที่มี Python เดินไปทำให้
ซึ่งแปลว่าในหน่วยงานที่ไม่มีคนแบบนั้น บัญชีที่ควรถูกปิดก็ยังเปิดอยู่

`spec.md` บันทึกช่องว่างนี้ไว้แล้วในชื่อ "เครื่องที่มีแต่ `.exe` สร้างบัญชีแรกไม่ได้"

## สิ่งที่ยังอยู่ที่เครื่องเซิร์ฟเวอร์เท่านั้น

**บัญชีแรก** แท็บนี้อยู่หลังด่าน มันจึงสร้างบัญชีแรกไม่ได้ตามนิยาม และเราจะไม่ทำหน้าที่
สร้างได้โดยไม่ต้องล็อกอิน ด้วยเหตุผลทั้งหมดใน ADR 0004 **ช่องว่างของเครื่องที่มีแต่ `.exe`
จึงยังไม่ถูกปิด** ทางแก้ที่น่าจะถูกคือให้ `app.py` รับคำสั่งย่อยชุดเดียวกันเมื่อมี argv
ไม่ใช่การเปิดหน้าเว็บให้

**การกู้คืนตอนที่ไม่เหลือใครเข้าได้** ถ้าบัญชีผู้ดูแลระบบทุกบัญชีถูกปิดหรือถูกล็อกพร้อมกัน
ไม่มีใครเปิดแท็บนี้ได้ `manage_users.py enable` และ `passwd` คือทางกลับทางเดียว ด้วยเหตุผล
เดียวกัน **คำสั่งใน CLI ไม่มีการตรวจอันดับบทบาท** คนที่นั่งหน้าเครื่องนั้นอยู่นอกระบบบทบาท
โดยนิยาม ตาม ADR 0004 ขอบเขตความปลอดภัยคือการเข้าถึงเครื่องทางกายภาพ การเติมกฎบทบาท
ลงไปใน CLI คือการปิดทางกลับทางเดียวที่มี

## กฎใหม่ของบทบาท และรูที่ต้องปิดไปพร้อมกัน

โจทย์ที่ได้มาคือ "ผู้ดูแลระบบทำได้ทุกอย่าง เจ้าหน้าที่สร้างและแก้ได้แต่ลบไม่ได้" อ่านตรงตัว
แล้วทำตามจะได้ระบบที่บทบาทไม่มีความหมาย: เจ้าหน้าที่สร้างบัญชีผู้ดูแลระบบให้ตัวเองได้ หรือ
ตั้งรหัสผ่านใหม่ให้บัญชีผู้ดูแลระบบแล้วเข้าไปใช้ ทั้งสองทางข้ามด่าน `require_admin` ที่เป็น
เส้นแบ่งเดียวของระบบนี้ไปได้ในสองคลิก

กฎที่ใช้จริงจึงเป็น **ห้ามมอบบทบาทที่สูงกว่าของตัวเอง และห้ามทำรายการกับบัญชีที่สูงกว่าตัวเอง**
ประโยคเดียวครอบทั้งสองทาง และเขียนไว้เป็นข้อมูลใน `USER_ACTIONS` ไม่ใช่ `if` ที่กระจายตาม
route (ดู `app.py` และ `tests/test_users.py`)

"ลบ" ในโจทย์กลายเป็น **ปิดบัญชี** ไม่ใช่การลบแถว เหตุผลมีอยู่แล้วใน `CLAUDE.md`: ชื่อผู้ใช้
ไปปรากฏในบันทึกว่าใครทำอะไร และถูกจองตลอดไป ถ้าชื่อเอากลับมาใช้ใหม่ได้ บันทึกเก่าจะชี้ไปที่
คนสองคนที่แยกกันไม่ออก ระบบนี้จึงไม่มีคำสั่งลบบัญชีทั้งใน CLI และบนเว็บ และไม่มี route
`DELETE /api/users` ให้ใครมาเขียนต่อครึ่งทาง

## ต้องเหลือผู้ดูแลระบบที่ใช้งานได้เสมอ

กฎ "ห้ามปิดหรือลดบทบาทตัวเอง" ครอบเกือบหมด ผู้ดูแลระบบคนสุดท้ายเอาตัวเองออกไม่ได้ และคนอื่น
ไม่ใช่คนสุดท้าย แต่มันพังเมื่อสอง request ทับกัน: ผู้ดูแลระบบสองคนสั่งปิดบัญชีของกันและกัน
พร้อมกัน ต่างคนต่างผ่านด่าน "ไม่ใช่ตัวเอง" ของตัวเอง และต่างคนต่างไม่ได้นับว่าเหลือกี่คน

ด่านจริงจึงเป็นการ **นับหลังเขียน** ภายใน transaction เดียวกัน ตรงนั้นอยู่ใน write lock ของ
SQLite แล้ว คนที่มาทีหลังจึงเห็นผลของคนแรก แล้ว rollback ทั้งก้อน การนับ *ก่อน* เขียนปิดรูนี้
ไม่ได้ เพราะมันอ่าน snapshot ที่ถ่ายไว้ก่อนได้ lock ทั้งสอง request จะเห็นเลขเดียวกันแล้วผ่าน
ทั้งคู่

ชุดเทสต์ปกติสร้างจังหวะนี้ไม่ได้ เพราะ test client ของ Flask เรียงลำดับ request ให้เสมอ
`tools/verify_user_management.py` จึงยกเซิร์ฟเวอร์จริงขึ้นมาแล้วยิงสองเธรดแข่งกัน 15 รอบ

## สิ่งที่ยอมรับ

**ทุกคนที่ล็อกอินได้เห็นรายชื่อบัญชีทั้งหมด** รวมถึงบัญชีผู้ดูแลระบบที่ตัวเองแตะไม่ได้
ทางเลือกคือซ่อนไป ซึ่งทำให้ข้อความ "มีผู้ใช้ชื่อนี้อยู่แล้ว" ตอนสร้างบัญชีอธิบายไม่ได้ และ
ในสำนักงานเดียวกันรายชื่อคนที่ใช้ระบบไม่ใช่ความลับ

**เจ้าหน้าที่สร้างบัญชีได้** ตามโจทย์ บัญชีเป็นแถวที่ลบไม่ได้ และการแก้ที่ทำได้คือปิดบัญชี
ถ้าวันหนึ่งเห็นว่าไม่ควร การแก้คือเปลี่ยน `min_role` ของ `user.create` เป็น `ROLE_ADMIN`
บรรทัดเดียว ไม่มีอย่างอื่นขยับตาม

**ไม่มีปุ่มปลดล็อกบัญชีที่ถูกล็อกชั่วคราว** มันปลดตัวเองใน 5 นาที และการตั้งรหัสผ่านใหม่
ปลดให้ทันทีอยู่แล้ว ป้าย "ล็อกชั่วคราว" บอกผู้ดูแลว่าเป็นกรณีไหน

**วันที่แสดงเป็น ค.ศ.** เหมือนคอลัมน์วันที่บันทึกของตารางรายการ ภาพตัวอย่างที่ใช้อ้างอิง
แสดงเป็น พ.ศ. แต่เป็นภาพจากโปรแกรมคนละตัว การทำตามภาพจะทำให้สองตารางในโปรแกรมเดียวกัน
ไม่ตรงกัน
